# Implantación de soluciones de alta disponibilidad

## 1. Definición y objetivos

## Resumen de conceptos

La **alta disponibilidad (High Availability, HA)** engloba las técnicas destinadas a conseguir que un sistema, aplicación, servicio o infraestructura permanezca operativo durante el mayor tiempo posible y pueda recuperarse rápidamente ante fallos.

Los principales objetivos son:

- Reducir el tiempo de indisponibilidad.
- Evitar puntos únicos de fallo.
- Mantener los servicios disponibles ante averías.
- Detectar automáticamente determinados fallos.
- Recuperar los servicios de forma rápida.
- Garantizar la integridad y consistencia de los datos.
- Distribuir la carga entre varios sistemas.
- Facilitar el mantenimiento sin detener completamente los servicios.
- Permitir la recuperación ante fallos de hardware, software o comunicaciones.

Una idea fundamental es:

> **Alta disponibilidad no significa que un sistema nunca falle, sino que está diseñado para que un fallo no provoque una interrupción prolongada del servicio.**

## Desarrollo teórico

Un sistema tradicional puede tener una arquitectura similar a esta:

```text
                    CLIENTES
                       |
                       v
                +-------------+
                |   SERVIDOR  |
                |     WEB     |
                +-------------+
                       |
                       v
                  ALMACENAMIENTO
```

Si el servidor falla, el servicio deja de estar disponible.

En una arquitectura de alta disponibilidad se introducen elementos redundantes:

```text
                         CLIENTES
                            |
                            v
                   +----------------+
                   |  BALANCEADOR   |
                   +----------------+
                     /            \
                    /              \
                   v                v
          +-------------+    +-------------+
          | SERVIDOR 1  |    | SERVIDOR 2  |
          +-------------+    +-------------+
                   \                /
                    \              /
                     v            v
                  +------------------+
                  | ALMACENAMIENTO   |
                  | COMPARTIDO/REP.  |
                  +------------------+
```

Si uno de los servidores deja de funcionar, el otro puede continuar proporcionando el servicio.

### Conceptos relacionados

**Disponibilidad**

Mide la proporción de tiempo durante la cual un servicio permanece operativo.

Una forma habitual de expresarla es:

```text
Disponibilidad (%) =
Tiempo disponible / Tiempo total × 100
```

Por ejemplo, si un servicio está disponible 8.750 horas de un total de 8.760 horas:

```text
Disponibilidad = 8750 / 8760 × 100 ≈ 99,89 %
```

### SLA

Un **SLA (Service Level Agreement)** establece los niveles de servicio comprometidos.

Puede especificar:

- Disponibilidad.
- Tiempo máximo de respuesta.
- Tiempo máximo de recuperación.
- Tiempo máximo de resolución.
- Procedimientos ante incidentes.

### MTBF y MTTR

Dos conceptos importantes son:

**MTBF (Mean Time Between Failures)**

Tiempo medio entre fallos.

**MTTR (Mean Time To Repair/Recover)**

Tiempo medio necesario para reparar o recuperar un servicio.

Una infraestructura de alta disponibilidad intenta:

- aumentar el MTBF;
- reducir el MTTR.

Por ejemplo:

```text
                DISPONIBILIDAD

       Prevención              Recuperación
           |                        |
           v                        v
   +---------------+        +---------------+
   | Redundancia   |        | Failover      |
   | Monitorización|        | Backup        |
   | Mantenimiento |        | Recuperación  |
   +---------------+        +---------------+
```

# 2. Análisis de configuraciones de alta disponibilidad

## Resumen de conceptos

Existen diferentes mecanismos para conseguir alta disponibilidad:

- Funcionamiento interrumpido.
- Balanceadores de carga.
- Almacenamiento compartido.
- Sistemas de archivos distribuidos o compartidos.
- Dispositivos de bloque.
- Servidores redundantes.
- Clusters.
- Replicación.
- Mecanismos de failover.
- Recuperación de servicio.
- Sistemas de monitorización.

No existe una única arquitectura válida para todos los escenarios. La solución depende del servicio, presupuesto, requisitos de disponibilidad y tolerancia al fallo.

---

## 2.1. Funcionamiento interrumpido y alta disponibilidad

### Resumen de conceptos

El objetivo es conseguir que el usuario pueda continuar utilizando el servicio aunque se produzca un fallo en alguno de los componentes.

Para conseguirlo pueden utilizarse:

- Redundancia.
- Failover.
- Clustering.
- Balanceo.
- Replicación.
- Almacenamiento redundante.
- Fuentes de alimentación redundantes.
- Redes redundantes.

### Desarrollo teórico

Una infraestructura puede contener múltiples puntos de fallo:

```text
                 INTERNET
                    |
                 ROUTER
                    |
                FIREWALL
                    |
               BALANCEADOR
                    |
              +-----+-----+
              |           |
          SERVIDOR A  SERVIDOR B
              |           |
              +-----+-----+
                    |
              ALMACENAMIENTO
```

Si solamente existe un firewall, por ejemplo, este puede convertirse en un **SPOF (Single Point of Failure)**.

Un punto único de fallo es un componente cuya avería provoca la interrupción del servicio.

La alta disponibilidad intenta eliminar estos puntos:

```text
                  INTERNET
                     |
              +------+------+
              |             |
          FIREWALL 1     FIREWALL 2
              |             |
              +------+------+
                     |
              +------+------+
              |             |
        BALANCEADOR 1   BALANCEADOR 2
              |             |
              +------+------+
                     |
          +----------+----------+
          |                     |
      SERVIDOR A           SERVIDOR B
```

### Failover

El **failover** consiste en pasar el servicio desde un componente que ha fallado a otro componente disponible.

```text
SERVIDOR A
    |
    | funcionamiento normal
    v
SERVICIO ACTIVO

        X FALLO

SERVIDOR B
    |
    | failover
    v
SERVICIO ACTIVO
```

El cambio puede ser:

- Automático.
- Manual.
- Semiautomático.

En una infraestructura de alta disponibilidad suele buscarse el failover automático cuando el escenario lo permite.

# 3. Balanceadores de carga

## Resumen de conceptos

Un **balanceador de carga (Load Balancer)** distribuye las peticiones entre varios servidores.

Sus objetivos son:

- Distribuir trabajo.
- Evitar la saturación de un servidor.
- Aumentar la capacidad.
- Mejorar la disponibilidad.
- Detectar servidores que no responden.
- Evitar enviar tráfico a servidores que están fuera de servicio.

## Desarrollo teórico

Sin balanceador:

```text
             CLIENTES
                 |
                 v
           SERVIDOR WEB
                 |
                 v
             SERVICIO
```

Con balanceador:

```text
                 CLIENTES
                     |
                     v
             +---------------+
             | LOAD BALANCER |
             +---------------+
               /     |      \
              /      |       \
             v       v        v
          WEB 1    WEB 2    WEB 3
```

Si `WEB 2` deja de funcionar:

```text
                 CLIENTES
                     |
                     v
             +---------------+
             | LOAD BALANCER |
             +---------------+
               /            \
              v              v
           WEB 1           WEB 3
```

El balanceador deja de enviar nuevas peticiones al servidor afectado.

### Algoritmos de balanceo

Entre los algoritmos habituales se encuentran:

| Algoritmo | Funcionamiento |
|---|---|
| Round Robin | Distribuye las peticiones secuencialmente |
| Weighted Round Robin | Distribuye según pesos |
| Least Connections | Envía tráfico al servidor con menos conexiones |
| Weighted Least Connections | Tiene en cuenta conexiones y capacidad |
| IP Hash | Asocia determinadas IP a servidores |
| Random | Selecciona servidores aleatoriamente |

### Health checks

Los balanceadores pueden realizar comprobaciones periódicas:

```text
Load Balancer
      |
      +----> ¿WEB 1 responde? ----> OK
      |
      +----> ¿WEB 2 responde? ----> ERROR
      |
      +----> ¿WEB 3 responde? ----> OK
```

Si un servidor no responde correctamente, puede retirarse temporalmente del conjunto de servidores disponibles.

# 4. Almacenamiento compartido

## Resumen de conceptos

Cuando varios servidores deben acceder a los mismos datos es necesario diseñar correctamente el almacenamiento.

Existen diferentes posibilidades:

- Sistemas de archivos compartidos.
- Almacenamiento en red.
- Dispositivos de bloque.
- SAN.
- NAS.
- Sistemas de archivos distribuidos.
- Replicación.

## Desarrollo teórico

Una arquitectura sencilla puede utilizar un almacenamiento compartido:

```text
       SERVIDOR A              SERVIDOR B
            |                       |
            +-----------+-----------+
                        |
                        v
               +----------------+
               | ALMACENAMIENTO |
               +----------------+
```

De esta forma ambos servidores pueden trabajar con la misma información.

### NAS

Un **NAS (Network Attached Storage)** proporciona almacenamiento mediante protocolos de acceso a archivos.

Ejemplo conceptual:

```text
Servidor A ----\
                \
Servidor B ------> NAS
                /
Servidor C ----/
```

### SAN

Una **SAN (Storage Area Network)** proporciona acceso a almacenamiento a nivel de bloque.

```text
SERVIDOR A ----\
                \
SERVIDOR B ------> SAN
                /
SERVIDOR C ----/
```

La diferencia conceptual es importante:

```text
NAS
 |
 +-- acceso a archivos

SAN
 |
 +-- acceso a bloques
```

### Dispositivos de bloque

El almacenamiento de bloque presenta al sistema un dispositivo que puede ser utilizado para crear sistemas de archivos o para otros usos.

Ejemplo:

```text
Servidor
   |
   v
Dispositivo de bloque
   |
   v
Sistema de archivos
   |
   v
Archivos y directorios
```

### Riesgos del almacenamiento compartido

El almacenamiento compartido también puede convertirse en un punto único de fallo.

Por ello puede ser necesario utilizar:

- RAID.
- Controladoras redundantes.
- Fuentes de alimentación redundantes.
- Caminos de acceso redundantes.
- Replicación.
- Almacenamiento distribuido.

# 5. Sistemas de archivos y dispositivos de bloque

## Resumen de conceptos

En una infraestructura de alta disponibilidad hay que distinguir entre:

- Acceso a archivos.
- Acceso a bloques.

Los sistemas de archivos gestionan estructuras como:

```text
/
├── etc
├── home
├── var
└── datos
```

Mientras que el almacenamiento de bloque proporciona unidades sobre las que el sistema operativo puede trabajar.

## Desarrollo teórico

Ejemplo:

```text
Aplicación
    |
    v
Sistema de archivos
    |
    v
Dispositivo de bloque
    |
    v
Almacenamiento
```

En entornos distribuidos pueden utilizarse sistemas de archivos diseñados para permitir el acceso desde diferentes nodos.

Hay que controlar especialmente:

- Bloqueos.
- Consistencia.
- Concurrencia.
- Corrupción de datos.
- Latencia.
- Replicación.

Un problema especialmente importante aparece cuando dos nodos intentan modificar simultáneamente los mismos datos sin mecanismos adecuados de coordinación.

# 6. Servidores redundantes

## Resumen de conceptos

La redundancia consiste en disponer de componentes adicionales que puedan asumir el servicio cuando otro componente falla.

Puede aplicarse a:

- Servidores.
- Discos.
- Fuentes de alimentación.
- Interfaces de red.
- Switches.
- Routers.
- Firewalls.
- Balanceadores.
- Sistemas de almacenamiento.

## Desarrollo teórico

### Active-Passive

En un sistema activo-pasivo un servidor presta el servicio y otro permanece preparado para asumirlo.

```text
             CLIENTES
                 |
                 v
          +-------------+
          | SERVIDOR A  |
          |   ACTIVO    |
          +-------------+
                 |
              FALLO
                 |
                 v
          +-------------+
          | SERVIDOR B  |
          |   PASIVO    |
          +-------------+
                 |
              ACTIVO
```

### Active-Active

En una configuración activo-activo varios servidores proporcionan servicio simultáneamente.

```text
             CLIENTES
                 |
                 v
          +-------------+
          | BALANCEADOR |
          +-------------+
             /       \
            v         v
       SERVIDOR A  SERVIDOR B
          ACTIVO      ACTIVO
```

Esto permite aprovechar simultáneamente los recursos disponibles.

### Comparación

| Arquitectura | Servidor principal | Aprovechamiento | Failover |
|---|---|---|---|
| Active-Passive | Uno | Menor | Sí |
| Active-Active | Varios | Mayor | Sí |

# 7. Sistemas de «clusters»

## Resumen de conceptos

Un **cluster** es un conjunto de sistemas que trabajan coordinadamente para proporcionar uno o varios servicios.

Los clusters pueden utilizarse para:

- Alta disponibilidad.
- Balanceo.
- Escalabilidad.
- Procesamiento distribuido.
- Recuperación ante fallos.

## Desarrollo teórico

Arquitectura conceptual:

```text
                 CLIENTES
                     |
                     v
              +-------------+
              |   CLUSTER   |
              +-------------+
                /    |    \
               /     |     \
              v      v      v
           NODE 1  NODE 2  NODE 3
```

Los nodos pueden estar supervisados mediante mecanismos de monitorización y coordinación.

### Componentes habituales

Un cluster puede incluir:

- Nodos.
- Red de comunicación.
- Mecanismo de coordinación.
- Sistema de almacenamiento.
- Monitorización.
- Gestión de recursos.
- Mecanismo de recuperación.

### Quorum

En determinados clusters se utiliza un mecanismo de **quorum** para determinar qué conjunto de nodos tiene derecho a prestar el servicio.

Esto ayuda a evitar situaciones en las que diferentes grupos de nodos intenten actuar simultáneamente como sistema activo.

### Split-brain

El **split-brain** aparece cuando los nodos de un cluster pierden la comunicación entre sí y diferentes grupos creen que deben continuar prestando el servicio.

Conceptualmente:

```text
       NODE 1       NODE 2
          \          /
           \        /
          X RED X
           /        \
          /          \
       NODE 3       NODE 4

     Grupo A        Grupo B
     "Estoy          "Estoy
      activo"         activo"
```

Es un problema importante en sistemas de alta disponibilidad y debe prevenirse mediante mecanismos de coordinación, quorum, fencing u otras técnicas apropiadas.

# 8. Integridad de datos y recuperación de servicio

## Resumen de conceptos

La disponibilidad por sí sola no es suficiente.

Un sistema puede estar funcionando y, sin embargo, proporcionar datos incorrectos o corruptos.

La alta disponibilidad debe combinar:

- Disponibilidad.
- Integridad.
- Consistencia.
- Recuperación.

## Desarrollo teórico

Un sistema debe ser capaz de responder a preguntas como:

- ¿Qué ocurre si falla un servidor?
- ¿Qué ocurre si falla un disco?
- ¿Qué ocurre si se corrompe una base de datos?
- ¿Qué ocurre si se pierde una conexión?
- ¿Qué ocurre si se modifica información incorrectamente?
- ¿Cuánto tiempo se tarda en recuperar el servicio?

### RPO

**RPO (Recovery Point Objective)** indica cuánta información se puede perder como máximo después de un incidente.

Ejemplo:

```text
RPO = 15 minutos
```

Significa que el diseño debe intentar limitar la pérdida de datos a aproximadamente 15 minutos.

### RTO

**RTO (Recovery Time Objective)** indica cuánto tiempo puede tardarse en recuperar el servicio.

Ejemplo:

```text
RTO = 30 minutos
```

Significa que el servicio debe diseñarse para poder recuperarse dentro de ese objetivo.

### Relación entre RPO y RTO

```text
              INCIDENTE
                  |
                  v
        +-------------------+
        | Pérdida de datos  | <-- RPO
        +-------------------+
                  |
                  v
        +-------------------+
        | Recuperar servicio| <-- RTO
        +-------------------+
                  |
                  v
              SERVICIO
              OPERATIVO
```

# 10. Virtualización de sistemas

## Resumen de conceptos

La **virtualización** permite ejecutar sistemas operativos y aplicaciones sobre recursos físicos abstraídos mediante una capa de virtualización.

Una máquina física puede ejecutar varias máquinas virtuales.

```text
+---------------------------------------+
|           SERVIDOR FÍSICO             |
|                                       |
|       +-------------------------+     |
|       |       HIPERVISOR        |     |
|       +-------------------------+     |
|          |        |        |          |
|          v        v        v          |
|        VM 1     VM 2     VM 3         |
|                                       |
+---------------------------------------+
```

---

# 11. Posibilidades de la virtualización de sistemas

## Resumen de conceptos

La virtualización permite:

- Consolidar servidores.
- Aprovechar mejor el hardware.
- Crear laboratorios.
- Separar servicios.
- Probar configuraciones.
- Crear entornos de desarrollo.
- Crear entornos de recuperación.
- Realizar snapshots.
- Migrar máquinas virtuales.
- Simular infraestructuras.
- Crear escenarios de alta disponibilidad.

## Desarrollo teórico

Un único servidor físico puede alojar:

```text
SERVIDOR FÍSICO
      |
      +-- VM 1 -> Servidor web
      |
      +-- VM 2 -> Base de datos
      |
      +-- VM 3 -> Servidor DNS
      |
      +-- VM 4 -> Servidor de monitorización
```

Esto resulta especialmente útil en formación porque permite crear laboratorios completos sin disponer de un servidor físico para cada servicio.

# 12. Herramientas para la virtualización

## Resumen de conceptos

Existen diferentes tecnologías y plataformas de virtualización.

Algunas herramientas habituales son:

- VMware.
- VirtualBox.
- Hyper-V.
- KVM/QEMU.
- Proxmox VE.
- Xen.

También existen soluciones de virtualización y contenedores que utilizan mecanismos diferentes.

## Desarrollo teórico

### Hipervisor de tipo 1

Se ejecuta directamente sobre el hardware.

```text
HARDWARE
   |
   v
HIPERVISOR
   |
   +-- VM 1
   +-- VM 2
   +-- VM 3
```

### Hipervisor de tipo 2

Se ejecuta sobre un sistema operativo convencional.

```text
HARDWARE
   |
   v
SISTEMA OPERATIVO
   |
   v
HIPERVISOR
   |
   +-- VM 1
   +-- VM 2
```

La elección depende de:

- Rendimiento.
- Compatibilidad.
- Administración.
- Coste.
- Hardware disponible.
- Requisitos del laboratorio.

# 13. Configuración y utilización de máquinas virtuales

## Resumen de conceptos

Una máquina virtual necesita recursos virtualizados:

- CPU.
- Memoria RAM.
- Disco.
- Interfaces de red.
- BIOS/UEFI virtual.
- Dispositivos virtuales.
- Sistema operativo.

## Desarrollo teórico

Una VM puede configurarse, por ejemplo, con:

```text
VM SERVIDOR WEB

CPU:       2 vCPU
RAM:       4 GB
DISCO:     40 GB
RED:       Adaptador virtual
SO:        Linux
```

### Red virtual

Las plataformas de virtualización suelen proporcionar diferentes modos de red.

Por ejemplo:

```text
NAT

VM ---> Hipervisor ---> Internet
```

```text
Bridge

VM ---------> Red física ---------> Internet/LAN
```

```text
Red interna

VM1 <------> VM2 <------> VM3
```

Esto permite crear laboratorios donde diferentes máquinas virtuales representan:

- Clientes.
- Servidores.
- Routers.
- Firewalls.
- Sistemas de monitorización.

# 14. Alta disponibilidad y virtualización

## Resumen de conceptos

La virtualización facilita la implantación de alta disponibilidad porque permite abstraer los servicios respecto al hardware físico.

Una máquina virtual puede, dependiendo de la plataforma y arquitectura:

- Migrarse.
- Replicarse.
- Restaurarse.
- Clonarse.
- Reiniciarse en otro nodo.
- Recuperarse desde una copia.

## Desarrollo teórico

Arquitectura conceptual:

```text
                  ALMACENAMIENTO
                        |
          +-------------+-------------+
          |                           |
          v                           v
     +---------+                 +---------+
     | HOST 1  |                 | HOST 2  |
     +---------+                 +---------+
       |     |                     |     |
       v     v                     v     v
      VM1   VM2                   VM3   VM4
```

Si `HOST 1` falla, las máquinas virtuales pueden recuperarse en `HOST 2` si la arquitectura lo permite.

```text
ANTES

HOST 1                    HOST 2
 VM1                       VM3
 VM2                       VM4


FALLO HOST 1
     X

HOST 2
 VM3
 VM4
 VM1
 VM2
```

La virtualización no garantiza por sí misma la alta disponibilidad.

Es necesario diseñar correctamente:

- Hosts redundantes.
- Almacenamiento.
- Red.
- Monitorización.
- Replicación.
- Recuperación.
- Gestión de recursos.

          CLIENTE 1         CLIENTE 2
              |                 |
              +--------+--------+
                       |
                       v
                 +-----------+
                 | FIREWALL  |
                 +-----------+
                       |

# 16. Pruebas de carga

## Resumen de conceptos

Las **pruebas de carga** permiten comprobar cómo se comporta un sistema cuando recibe diferentes niveles de trabajo.

Sirven para analizar:

- Capacidad.
- Rendimiento.
- Tiempo de respuesta.
- Uso de CPU.
- Uso de memoria.
- Red.
- Almacenamiento.
- Número máximo de usuarios.
- Comportamiento ante saturación.

## Desarrollo teórico

Una prueba puede incrementar progresivamente el número de peticiones:

```text
Usuarios
   |
   |                         ______
   |                    ____/
   |               ____/
   |          ____/
   |     ____/
   |____/
   +-----------------------------> Tiempo
```

Se observa cómo responde el sistema.

### Métricas

Algunas métricas habituales son:

| Métrica | Qué mide |
|---|---|
| Throughput | Trabajo procesado por unidad de tiempo |
| Latencia | Tiempo necesario para responder |
| CPU | Utilización del procesador |
| RAM | Memoria utilizada |
| I/O | Operaciones de entrada/salida |
| Ancho de banda | Tráfico de red |
| Errores | Peticiones fallidas |
| Conexiones | Conexiones simultáneas |

# 17. Cargas sintéticas

## Resumen de conceptos

Una **carga sintética** consiste en generar artificialmente actividad para comprobar el comportamiento de una infraestructura.

Permite realizar pruebas sin esperar a que aparezca tráfico real.

## Desarrollo teórico

Por ejemplo:

```text
             GENERADOR DE CARGA
                     |
                     v
             +---------------+
             | LOAD BALANCER |
             +---------------+
                /          \
               v            v
            WEB 1         WEB 2
```

El generador puede aumentar progresivamente la carga:

```text
100 usuarios
     |
     v
500 usuarios
     |
     v
1.000 usuarios
     |
     v
2.000 usuarios
     |
     v
5.000 usuarios
```

Durante el proceso se monitoriza el sistema.

### Objetivo

No se trata simplemente de saturar un servidor.

Hay que determinar:

- Cuándo aumenta la latencia.
- Cuándo aparecen errores.
- Qué componente se convierte en cuello de botella.
- Si el balanceador distribuye correctamente.
- Si los servidores soportan la carga.
- Si el sistema escala.
- Qué sucede cuando falla un nodo.

# 19. Metodología para implantar alta disponibilidad

## Resumen de conceptos

Una metodología ordenada permite evitar que la alta disponibilidad se limite a instalar dos servidores.

## Desarrollo teórico

### Fase 1. Identificar servicios críticos

Por ejemplo:

```text
DNS
WEB
BASE DE DATOS
CORREO
APLICACIONES
ALMACENAMIENTO
```

### Fase 2. Identificar puntos únicos de fallo

```text
¿Existe un único servidor?
¿Existe un único disco?
¿Existe un único switch?
¿Existe un único firewall?
¿Existe un único enlace?
```

### Fase 3. Determinar RTO y RPO

```text
Servicio A
RTO = 5 minutos
RPO = 1 minuto

Servicio B
RTO = 2 horas
RPO = 24 horas
```

No todos los servicios necesitan el mismo nivel de disponibilidad.

### Fase 4. Diseñar redundancia

```text
          COMPONENTE
               |
        +------+------+
        |             |
      ACTIVO        RESERVA
```

### Fase 5. Implantar

Configurar:

- Servidores.
- Red.
- Almacenamiento.
- Balanceadores.
- Clusters.
- Monitorización.

### Fase 6. Probar

Realizar:

- Pruebas de carga.
- Pruebas de failover.
- Pruebas de recuperación.
- Pruebas de pérdida de conectividad.
- Pruebas de almacenamiento.
- Pruebas de integridad.

### Fase 7. Monitorizar

Una infraestructura HA debe supervisarse continuamente.

# 21. Alta disponibilidad, escalabilidad y tolerancia a fallos

## Resumen de conceptos

Son conceptos relacionados, pero no equivalentes.

| Concepto | Objetivo |
|---|---|
| Alta disponibilidad | Mantener el servicio operativo |
| Tolerancia a fallos | Continuar funcionando ante fallos |
| Escalabilidad | Aumentar capacidad |
| Balanceo | Distribuir carga |
| Recuperación ante desastres | Recuperar servicios tras incidentes graves |
| Redundancia | Disponer de recursos alternativos |

Por ejemplo, añadir un segundo servidor puede mejorar la disponibilidad y también aumentar la capacidad.

Pero ambas propiedades no son exactamente lo mismo.

- Hipervisores.
- Clusters.
- Interfaces de administración.
- Redes.
- Almacenamiento.
- Balanceadores.

También deben controlarse:

- Autenticación.
- Autorización.
- Cifrado.
- Segmentación de red.
- Actualizaciones.
- Registro de eventos.
- Acceso administrativo.

# 25. Idea global para explicar al alumnado

La idea principal que debe quedar clara es que **la alta disponibilidad no consiste simplemente en tener dos servidores**.

Una infraestructura realmente disponible debe responder a varias preguntas:

```text
¿Qué ocurre si falla un servidor?
            |
            v
       FAILOVER


¿Qué ocurre si aumenta la carga?
            |
            v
       BALANCEO


¿Qué ocurre si falla el almacenamiento?
            |
            v
       REDUNDANCIA


¿Qué ocurre si se corrompen los datos?
            |
            v
       RECUPERACIÓN


¿Qué ocurre si falla el host físico?
            |
            v
       VIRTUALIZACIÓN / CLUSTER


¿Cómo sabemos que funciona?
            |
            v
       MONITORIZACIÓN


¿Cómo sabemos que soporta la carga?
            |
            v
       PRUEBAS DE CARGA
```

La arquitectura completa puede resumirse así:

```text
                         USUARIOS
                            |
                            v
                    +---------------+
                    | BALANCEADORES  |
                    +---------------+
                       /           \
                      v             v
                +---------+     +---------+
                | SERV. 1 |     | SERV. 2 |
                +---------+     +---------+
                      \             /
                       \           /
                        v         v
                     +-------------+
                     |   CLUSTER   |
                     +-------------+
                           |
                           v
                    +-------------+
                    | STORAGE HA  |
                    +-------------+
                           |
                           v
                    COPIAS / RÉPLICAS
                           |
                           v
                       RECUPERACIÓN
```

La secuencia conceptual que se puede utilizar en clase es:

**redundancia → monitorización → detección del fallo → failover → continuidad del servicio → recuperación → pruebas de carga → validación de la disponibilidad.**
